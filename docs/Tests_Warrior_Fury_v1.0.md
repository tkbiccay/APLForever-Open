### Critical harness finding — why the initial ON test failed

The first valid-distance 36-world run found Current/shipped both accepted Charge/Intercept even when OFF, and the in-memory guarded comparison blocked even ON: **34/36 green, both ON cases failed**. We then confirmed `DB.profile.toggles.movement.value`, `Engine.settings.toggles.movement.value`, `State.toggle.movement` were all **true BEFORE** the world run. Moving assignment before import did not help.

**Root cause proven from released source:** `tests/Game/harness/loop.lua:390` **explicitly overwrites `profile.toggles.movement.value = (R ~= nil)` for every driver before any non-replay loop**. This baseline fixture intentionally forces Movement OFF for natural-loop tests. The true value at end of run was **false**, disproving the original inference of an addon expression/eligibility fault. The v0.8.6 native test now uses its supplied `on` hook to **restore the chosen ON or OFF after the fixture-only reset** (starting on the first world tick) for the subsequent source-combat evaluations. The plugin's APL parser, state logic, ability source, world spell effects and all other toggles remain unmodified. The probe asserts the expected harness reset and reapplication to prevent a false pass if upstream changes its reset. **Do not copy this test-fixture method into an APL or infer the addon itself forces Movement OFF.** Warrior's `NewClass` lacks Druid's `movement=true` UI opt-in; this is a separate **in-game toggle discoverability/enablement question**, not proof of failed APL expression support.

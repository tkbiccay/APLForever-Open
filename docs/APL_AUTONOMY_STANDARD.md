# APL autonomy standard — one fully self-controlled rotation per supported Forever role

**Adopted 20 November 2026 by the maintainer, across all 28 intended roles (23 currently supported; five healer roles blocked).** This is a development/acceptance contract, not evidence that every existing candidate already conforms. The last-reported-working APL, shipped default and historical revisions remain byte-for-byte protected.

## Expected gameplay

The intended experience is **import, select and play**. Each supported, approved APL must make its own *routine* recommendations from the available source-verified Hekili Forever/Belief observations. The player should not need to visit class/spec pages or tick boxes to enable upkeep, curse/seal/poison/imbue choice, normal damage, pet recovery, forms/stances, threat/mitigation maintenance, safe resource conversion, target-mode choice or final fallback. These decisions belong in that role's complete standalone priority — no shared Lua files, cross-APL helpers or custom runtime add-ons.

**Source-pinned APL language reference:** [Hekili Forever v0.10.0 expressions, line options, local windows, pure variables, sequences and limitations](knowledge/engine/FOREVER_APL_SYNTAX_v0.10.0.md). Reuse verified cross-role syntax without re-searching, and recheck after release changes.

**Important distinction:** Hekili's generic toggles can be *user off-switches*, not a hidden prerequisite to a functioning rotation. The upstream [v0.10.0 Toggles documentation](https://github.com/zmsl/hekili/blob/v0.10.0/docs/wiki/Toggles.md) states an ability's **Require Toggle** assignment makes it unusable whenever that toggle is OFF, even if an APL line has no `if=toggle.*`. A pure APL **cannot override this engine contract**. Therefore respect a deliberate player OFF, use source-registered categories honestly and document an unavoidable engine restriction; do **not** promise all Major/Minor/Defensive/Interrupt/Potion abilities will trigger with their off-switches OFF.

## Design rules

1. **Zero manual dependency for routine decisions.** A newly authored APL must not use a `settings.<key>` per-spec dropdown or checkbox as the *condition required to make its normal rotation work*. Prefer observed ability knowledge, cost, aura status, proc, combat mode, threat, pet/form, attack eligibility and conservative resources. A test must run with stock defaults, no user activation. Never add an arbitrary custom setting to make a suggested recommendation possible.
2. **Automatic upkeep, not spam.** Debuffs, buffs, auras, seals, poisons and pet states use verified eligibility, refresh thresholds, resources and appropriate encounter value. Short solo fights, long bosses, grouped tanking, range uncertainty and low-level kits differ. Avoid overcasting 10-Rage or full-GCD upkeep on disposable mobs or repeated unsafe fallbacks.
3. **Automatic optional ability timing when allowed.** Design Major/Minor cooldowns, defensives, movement and interrupts around actual mechanics rather than requiring the player to choose timing by tick boxes; *still* respect explicit OFF and native Require Toggle restrictions, separate optional utility/potions from ordinary rotation. Do not hide a necessary throughput filler, pet recovery or routine tank debuff behind an optional cooldown toggle. For hidden/secret combat state, fail safe or document that a tactical ability remains manual.
4. **AoE is observability-limited.** Use `active_enemies` and known target/count/range signals where truthful. In instances and with absent nameplates Hekili may only report 1 target; the APL cannot secretly detect enemies. Document the real need for manual display/target-mode correction rather than pretending fully automatic AoE always works.
5. **No invented reads, no blanket changes.** Use the [pinned Forever APL conditions](https://github.com/zmsl/hekili/blob/v0.10.0/docs/wiki/APL-Conditions-On-Forever.md), exact registered abilities and fallback semantics. `target.is_boss`, `tanking`, `time`, `target.within5`, estimated Rage and hidden health have documented limitations. Test source-native first; no unmeasured DPS/survival improvements.
6. **Fully standalone import.** Every action/list/fallback and talent/rank/level branch lives inside that APL's own import file. No other role's APL, external helper or optional plugin should be necessary for castability.
7. **Respect the user's choices.** The player need not manage tick boxes to run the normal rotation. But actively disabling Major/Minor, Defensive, Interrupt, Movement, Potions or a named ability is a real opt-out, not permission for the APL to ignore consent or override the engine's setting.

## Capability-first opportunity gate — required for each NEW design/major revision

**The shipped default is not an architectural ceiling; absence of advanced syntax is not a defect by itself.** Before writing each full custom APL, compare its current source-registered class kit and shipped recipe against the [Forever v0.10.0 syntax reference](knowledge/engine/FOREVER_APL_SYNTAX_v0.10.0.md), the exact class source, registered cooldown/ability toggles, Belief and known limitations. Use the existing [knowledge per class](../knowledge/README.md) and tests; do not repeat full source research for tiny fixes.

1. **Discover capabilities:** spell/rank/talent/racial registration, action usability, cost and resource low/high belief bounds, aura/proc/ICD, native windows and their opening/step semantics, Auto Shot/next-swing interactions, pets/guardians, forms/stances, gear, supported damage/movement/interrupt abilities and actual toggle registrations. Record the difference between exposed, estimated, hidden/fixed, and manually controlled signals. Only a documented source key is eligible.
2. **Design alternatives by *causal hypothesis*:** independent priority (control); native window/sequence/pure variable only if it changes a useful decision; fallback-safe range/timing-aware hybrid when justified. No cargo-cult windows or variables solely to look advanced. Never turn an optional experimental feature into a required checkbox.
3. **Match default, last working and candidate:** true source-accepted action chains at legal and edge ranges, early/late game, target swaps, extreme resources, cooldown toggles OFF/ON and all Final Fallback / Repeated Recommendation paths. For timing hypotheses, count actions/refusals, stale recommendations, no-action tails and **causal** changes; for output hypotheses, test real damage or label output unmeasured. No fabricated source-state transitions, no pass by only asserting that imports succeed.
4. **Make explicit adoption decision:** `Adopt` only on reliable improvement without safety/regression; `Reject` on reproducible missed casts, no-action tail, toggle dependency or worse castability; `Inconclusive` protects last working; `Blocked` records missing state or gameplay evidence. Preserve exact negative comparator and export a reusable general lesson, then move on. Important: even a **green exploratory native suite** can measure a losing architecture.

**Concrete November 20 example (Guardian and BM equal P0):** v0.10.0 Hunter BM's class-provided `window.hha` is real, but an in-memory pure-HHA gate got **2 Hawk casts instead of 5** at 6yd versus the existing standalone BM v1.2 in the same 42s source-world test, because its Arcane step requires 8yd. [Draft experimental PR #24](https://github.com/tkbiccay/APLForever-Open/pull/24) records the result and rejects unconditional HHA; **do not silently install it**. Guardian's unrelated fifth-revision broad preflight was a test leak: the v0.9.0 engine allows **4 outside display subscribers**, but the harness subscribed once per protected revision. [Draft PR #22](https://github.com/tkbiccay/APLForever-Open/pull/22) fixes the test to subscribe once per *role*; await clean full regression before saying the Guardian candidate passed. Transfer the tested subscriber-lifetime lesson to other role test harnesses, not the APLs.

### Hidden semantic dependency: `tanking` / client role

Before an APL uses `tanking` as a necessary condition for a **routine tank/debuff or defensive action**, verify the published source and **actual client-reported role**. Forever v0.10.0 derives `tanking = role.tank and aggro`, but `role.tank` comes from `GetSpecializationInfo()` client role—not the selected custom Guardian APL. [Native test 44711863340](https://github.com/tkbiccay/APLForever-Open/actions/runs/44711863340) confirms the current published Feral **and Guardian** fake clients report `DAMAGER`, so both have `tanking=false`; the real user's client remains **unverified**. A source-supported conditional that never becomes true is a serious APL reachability issue, not a valid defensive. Use verified available alternative signals only with role-specific safety: group, time and actual observed aggro have distinct game/API limitations.

**Compare actual game defaults**, not just harness `sim` defaults. Forever's registered `settings.maintain_demoralizing_roar` is `false` normally but `sim=true` to represent a raid tank in the simulator. [Four-profile experiment 44713464837](https://github.com/tkbiccay/APLForever-Open/actions/runs/44713464837) proves this can reverse shipped/default Roar counts without changing the APL. Reproduce both configurations explicitly where relevant, and never promote an alternative merely for extra accepted casts without real threat/mitigation/output evidence.

## Lean execution and message delivery

**Operating principle:** maximise proof per GitHub/ChatGPT operation; improving original, standalone APL gameplay takes priority over maintaining CI machinery.

1. **One bounded engineering decision per interaction:** inspect latest pinned source, protected catalogue and handover, choose Guardian Tank / Hunter BM (equal P0) before Feral DPS; define one hypothesis, acceptance and rollback. Stop if a source/engine/gameplay gate is already decisive.
2. **Re-use existing evidence:** cache release pins, fixture quirks, known failures and cross-spec lessons. Do not reread every guide, role or source file for a narrowly verified fix. Research broadly only for a new spec, major upstream revision or real mechanical disagreement.
3. **Narrow tests before broad CI:** run the smallest source-native regression that tests both positive and negative branches; retain exact real accepted actions, refusals, toggles and fallback coverage. Run a broader suite only at a candidate/release boundary or when a shared harness/data/engine change creates meaningful cross-role risk. Never claim an unfinished run green.
4. **No repeated polling:** dispatch once, record SHA and Actions URL, check status once when useful. If still running, mark **Pending** and continue on the next interaction; do not keep the ChatGPT response open just to watch CI. Recheck already completed runs before dispatching duplicates.
5. **Atomic, low-churn GitHub writes:** combine related changes into one reviewable Draft commit when practical; use exact branch-head and file/hash preconditions, protect every existing APL and rollback. Avoid multiple comments/docs edits that restate identical evidence. Never silently merge, select, approve or overwrite the user's working APL.
6. **Delivery resilience:** provide concise results and links; for large work, share a durable result as soon as supported. After a response or tool timeout, first inspect GitHub commit and run state before retrying—successful writes may already exist. Keep complete APL code in source files and supply its entire copy-ready text when delivering the APL.
7. **Codex only when justified:** delegate distinct, sufficiently complex tasks with a concrete acceptance test that cannot efficiently be done in the current workflow. No delegation for ordinary status checks, single-line docs, routine fixture diagnosis or repeated broad scans.

**Status labels and stop rule:** Static / Source-Native / In-Game are different evidence grades; no real-client proof means no Approved status. If only the player can verify pet arrival, threat/role or a hidden-state behaviour, provide the smallest safe gameplay check and stop inventing headless equivalents. Protect last-working behaviour even when a simulation looks attractive.

## Mandatory all-role audit and promotion gates

- The repository's `scripts/audit_apl_controls.py` scans **every catalogue revision**, not just the newest, for `settings.*` and `toggle.*`. All previously reported uses are tied to **exact protected path and SHA-256**; a brand-new unreviewed `settings.*` dependency fails the static guard. Historical baseline exemption is *not* a certificate of autonomously correct behaviour. Toggle occurrences are **review findings**, not automatic defects; classify each ability and call-site by role/function.
- Prioritise **Guardian and Hunter BM equally**, followed by Feral DPS and risk-ranked roles. Check inherited old-state references before spending credit. Guardian v1.0 and Demonology v1.0 are user-reported working rollbacks: DO NOT rewrite their exact source merely to pass this new policy. Build independent full candidate, test against shipped/default and last working and preserve hashes.
- Guardian v1.2 gates routine Demoralising Roar behind Defensives, while v1.3 historically used `settings.maintain_demoralizing_roar`; **v1.4 Draft** replaces both with an autonomous source-visible boss/grouped/long-solo policy. Its focused 24-case v0.10.0 gate passed, but its broader v0.9.0 import lane **FAILED**, so it is *not* fully validated or ready for promotion. Hunter BM pet recovery/temporary guardians remain their own separate evidence gate. Demonology's assigned curse currently uses a class-setting dropdown; evaluate independent safe curse choice with the source's debuff/debuff-slot/group mechanics before creating a new candidate.
- Special high-value review: Paladin Protection's Holy Shield currently has a Defensives guard; assess whether this is **core mitigation** incorrectly hidden behind an optional toggle. Druid Balance, Mage Arcane/Fire/Frost and Elemental/Enhancement Shaman place some mana recovery under `toggle.cooldowns`; inspect the exact named resource action before changing, since registered cooldowns may be deliberately controlled by the engine. Also check any damage/utility moves under Movement or Minor Cooldowns; don't falsely call all toggles bugs.
- **Each changed role** must show default/no-manual-setup source-native imports, all option OFF/ON comparisons, honest engine-owned Require Toggle handling, 1–60 unlocks, resource extremes, ST/2/3+ when observable, opener, three source-accepted subsequent recommendations, **Final Fallback / Repeated Recommendation**, and shortest necessary in-game evidence. Anything unobservable is **Engine Limitation / Needs In-Game**, never a fabricated native PASS. No mass auto-promotion and no forced spec-wide rewrite.

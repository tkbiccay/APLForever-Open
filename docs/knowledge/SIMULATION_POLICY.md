# Optional simulation policy — APL-first, Hekili Forever first

**Decision: 18 November 2026.** This is a *reference and optional verification method*, **not a required workstream, prerequisite for a working APL, or the next default development task**. Owner direction supersedes any older handover/research text that calls for building a WoWSims bridge next.

## Non-negotiable priority

1. **Design the best independently importable Forever APL for the supported role.** Build the FULL self-contained priority, including precombat, upkeep, levels/talents, ST/AoE when observable, procs, resources, CDs, Defensives/Movement toggles, utility, pet/form, items and safe final fallbacks. Consider creative architectures, not merely shipped-default tweaks.
2. **Prove it works in released `zmsl/hekili`, using the actual Hekili Forever engine, registered kit, and its Belief/observer limits.** Preserve exact shipped default and protected Current/last-working comparators. Run source-native import/compile and focused cast progression with natural resources, changed state, accepted/refused actions and three successive post-upkeep/final-fallback recommendations. Fix actual reliability, safety, missing coverage and flicker before cosmetic optimisation.
3. **Refine and validate.** Diagnose APL vs engine/API vs headless fixture, reuse earlier regression lessons, compare fair/default/working behaviour and request only irreducibly live `/hek snap` evidence; never promote without in-game validation and owner approval.
4. **Only optionally run damage/threat/healing sims** when a *specific consequential decision* between two already source-safe, castable candidates remains unresolved and a simulator faithfully models the relevant Forever mechanics. Do **not** automatically follow a passing test with another sim/bridge task. Skip optional sim engineering while important APL correctness, coverage or gameplay-reliability gaps remain.

**Gate to authorise an optional sim:** Name the role/APL hashes, competing policies, real decision that output would change, pinned engine and combat/state-equivalence proof, minimal encounter, baseline/control, cost, acceptance/noise/rollback and STOP criterion. If Hekili Belief semantics cannot be reproduced in the other engine, label **Not Comparable**; native WoWSims adaptive APL scores never prove a Hekili import wins. Source-native Hekili *rotation-loop testing* is part of the **mandatory correctness gate**; WoWSims/Raidbots/SimC/AskMrRobot-style numerical output modelling is **optional** and must not replace it.

## Encounter labels, not separate profiles

These are reusable **test categories**, not claims about which encounters exist in WoW Forever or independent production APLs:

| Label | Damageable units | Incoming pressure and what to test |
| --- | --- | --- |
| Stationary boss / Patchwerk | 1 boss | ST uptime, resources, cooldowns, threat and boss-level damage/mitigation; boss damage strength is **separate** from target count |
| Boss + add cleave | Boss + 1 add (=2) | Position/uptime, add priority and swaps; expressly pin whether the add attacks the tank or another unit |
| Boss + four adds / 5-target mixed | Boss + 4 adds (=5) | AoE vs boss priority, movement/add duration and target switching; define each add's damageability and attacks independently |
| Dungeon pack / 5+ trash | 5 or more trash targets, optionally no boss | Pack-specific AoE, short fight/frequent pulls, resource carryover, survival/multi-target threat; **not synonymous with boss + adds or actual M+ availability** |
| Levelling, elite, recovery | 1–3 appropriately levelled opponents | Levels 1–60, unlocks, health/mana/Rage/Energy sustainability, travel/solo safety and repeated fallback |

For simplicity 1/2/5 **stationary damageable targets** are useful first controls. A realistic wave-spawn or dungeon-route model is optional, separate, and more expensive. Hold incoming enemy attack count/damage *constant* when isolating offensive target-count scaling; vary incoming threat deliberately **only** in a distinct survival scenario. Five simultaneous full-strength raid bosses hitting a solo tank is a different, often invalid experiment, not a standard five-target DPS test.

**Interpretation, sourced as methodology only:** [SimulationCraft predefined RaidEvents](https://github.com/simulationcraft/simc/wiki/RaidEvents) distinguishes Patchwerk, CleaveAdd, HecticAddCleave and DungeonSlice; [Raidbots' reliability warning](https://support.raidbots.com/article/43-unreliable-fight-styles) says some fight styles fail for individual specs. [SimulationCraft tank notes](https://github.com/simulationcraft/simc/wiki/SimcForTanks) explain incoming boss attacks, heals, DTPS/HPS/absorb and tank-metric interpretation; [Ask Mr Robot healer modelling](https://www.askmrrobot.com/articles/healing-optimization) emphasises healing demand, mana, movement and overheal. [Ask Mr Robot simulator design](https://www.askmrrobot.com/articles/a-new-kind-of-simulator) illustrates handling stochastic variance. [WoWSims Forever](https://github.com/wowsims/forever) is a distinct Forever-targeted native combat model. **These sources explain evaluation principles, not transferable Retail spells, mechanics, scripts, DPS figures, Forever encounter support or a valid Hekili→WoWSims translation.** Verify exact versions/source for every mechanic.

## Role-specific acceptance and reuse

- **DPS:** castability, stable action recommendation, near-zero unjustified idle GCDs, damage/DoT/proc/CD/resource and threat safety first. If numeric output is justified later, compare *total actual damage* under identical pin/gear/talents/toggles/fight, with variance; no cast-count-as-DPS shortcuts.
- **Tank:** mitigation/survival, dangerous damage spikes, deaths, threat and target control first; damage is secondary. Incoming attackers, artificial heals and enemy ranks must be explicitly declared. No guaranteed survival from synthetic permanent healing.
- **Healer:** only design/validate triage where released Hekili Forever can **actually observe and act on** player/party health and intent. The catalogue's five blocked healer roles **stay blocked** without a verified engine/API breakthrough. If a trustworthy later simulation is possible, measure *effective healing, overheal, prevented deaths, mana sustainability, cooldown timing and useful downtime DPS*, not raw HPS alone; an artificial pulse/fixed HPS model is **not an independent healer APL simulation**.

**Reuse across specs:** share **verified role-specific scenario designs, threat/mitigation/healing-demand methodology, normalised metrics, parsers, harnesses, regression cases and root-cause lessons** within the same role, extending cross-role only where the actual mechanism is shared. Preserve each class/spec's own rank/cost/talent/Belief/target/fallback conditions and compare its own shipped/working baselines; never share runtime APL dependencies or paste unverifiable spell logic across specs. Register validated lessons in [CROSS_APL_TRANSFER.md](lessons/CROSS_APL_TRANSFER.md) when resolving a real issue; do not create a universal sim suite merely because it can run.

# Validation, preservation, and promotion

`support_status` describes whether a role is known to be supported. `validation_status` describes the state of evidence for a particular configuration. They are separate fields. All roles begin `Unknown`; null references mean no APL has been supplied.

Each supplied revision records its canonical path, lifecycle status, SHA-256 of exact file bytes, available game/addon/build and character setup details, evidence, test results, and rollback reference. SHA-256 detects content changes; it does not prove code is valid or effective. Referenced files must exist. Preferred, last-working, last-approved, and shipped-default references must resolve to a revision with a matching hash. Keep former revisions in the repository and Git history.

**Self-contained import invariant:** Each supported role's selected or candidate APL must be **a complete standalone file** that imports and compiles in the pinned Hekili Forever environment *without any other custom APL, shared priority file or runtime helper*. Define every referenced custom list, precombat/combat branch, defensives, cooldowns, conditions and fallback **within that file**. A `call_action_list` must only call a list defined in its own file; no cross-profile calls, external custom `include`/`import` files, or shared runtime actions. The verified built-in Hekili Forever engine/class pack and game API are permitted dependencies. Use the existing native importer/compile checks and full reachable fallback/repeated-action checks to assess standalone behaviour. **Shared research, fixture helpers, regression tests and development tooling are permitted**; they must never be necessary for the imported APL to function in the game. A library-wide lesson may be reused in a new self-contained APL only after the spec's mechanic and castability checks.

Promotion path: `Draft` → `StaticValidated` → `PendingInGame` → `InGameValidated` → `Approved`. `ReportedWorking`, `NeedsRetest`, and `Retired` are additional states, not shortcuts to approval. Keep a candidate separate until review. Do not replace a preferred or last-working configuration automatically or in place.

Default promotion target is **one adaptive preferred APL for each supported `<Class>_<Spec>` primary role**, expected to behave at levels 1–60 and in level-60 open world/dungeon/raid conditions. No automatic Levelling/Endgame duplication. A split requires documented evidence of an engine/intent limit, fair matched benefit, extra maintenance cost and explicit exception approval. Do not assume that reaching level 60 implies a raid encounter.

Before approval, preserve the exact baseline, describe the candidate diff, verify syntax using a verified method where available, audit every priority and final fallback, check known regressions, compare with shipped default and last-working versions, **verify that the APL optimises its declared class/spec and primary role; permit source-verified cross-tree builds and same-role hybrid weaving while rejecting unsupported or unsafe role switching**, verify the exact `<Class>_<Spec>` import name, record real in-game evidence and test results, and obtain human approval. Archived mixed-style designs require normal source, final-fallback and in-game review, not automatic replacement merely because they mix legitimate combat styles. An `Approved` entry must have `Supported` support classification and evidence identifying in-game validation. CI never approves or promotes configurations.

`python scripts/validate_repository.py` checks identifiers, metadata, canonical filenames, references, hashes, approval evidence, and available Git baseline preservation. It reports when there is no usable Git baseline. It intentionally does not invent an APL parser.

**Resolved-issue learning and cross-APL transfer (mandatory):** After resolving an issue, complete the [cross-APL applicability checkpoint](knowledge/lessons/CROSS_APL_TRANSFER.md). Pin the confirmed cause and test, distinguish source/engine/fixture faults from combat APL defects, identify genuinely affected roles and explicit exclusions, and either reuse the verified method, request the *smallest* role-specific check, or record why there is no safe transfer. Include the outcome in the existing issue/test/PR rather than spawning duplicate documents or broad test sprints. A shared diagnosis **does not** authorise silently changing another class's rotation, skipping its source/castability/final-fallback checks, or displacing a working Checkpoint. If the original evidence already resolves the question, record **STOP** and spend no further Codex/CI credits.
